## Product Intent

- This app is a deliberately slower, more intentional video-watching interface: a "disconnected" alternative to the main YouTube experience.
- The core promise is user control: chronological subscription feeds, watch later/library flows, schedules, usage limits, channel filters, break warnings, no-thumbnail mode, and curated recommendations that can be turned down or shaped.
- The project is still building fundamental features. Prefer changes that strengthen the app's underlying behavior and settings model over surface polish that makes it look like a generic video platform.
- The longer-term deployment goal is self-hosting: a person should be able to fork/deploy it on their own Vercel + Supabase + Google API credentials and share that instance with a small trusted group, such as 5-10 friends.

## Brand And Legal Caution

- Do not present this as an official YouTube or Google product.
- Avoid copying YouTube trade dress beyond what is necessary for interoperability with embedded videos. Future UI work should move toward a custom identity and more user customizability.
- Be careful with names, copy, colors, icons, and layouts that make the app feel like a YouTube clone. Prefer language like "video feed", "library", "watch limits", "channel filters", and "recommendations" unless a YouTube API concept is being referenced directly.
- The app uses YouTube Data API and YouTube IFrame embeds, so users deploying it are responsible for Google/YouTube API Terms compliance. Agents should not claim that public distribution is legally or ToS-safe.
- For small-group sharing features, keep privacy, quota, access control, and user consent in mind. This is product guidance, not legal advice.

## Brand Icons

- The icons come from the Villow icon kit; version 3 (2026-09-20) is installed. Its master copy lives in the design repo (`villow_logo_testing/villow-icons`), and it is a hand-off, not a dependency: a new version is dropped at this repo's root as `villow-icons/`, installed by following its `UPDATE-PROMPT.md` (or `AI-INSTRUCTIONS.md` for a first install), then deleted so a stale copy can never ship. `.vercelignore` keeps it out of deploys while it is here. Never link to it from production code, and never recolour, resize, re-export or outline a kit file.
- The mark has three cuts, chosen by the height it is **drawn** at, not the file's size: as drawn from 33px, with the gap tapering to a point at the tip; `small` at 21-32px, a 40-unit even lane; `micro` at 20px and under, a 56-unit lane. The lanes are cut along a line that carries on past the sail's tip, so the swoosh's end runs straight out instead of hooking back up. The kit's PNG and ICO files already carry the right cut for each size, and `favicon.svg` and the pinned tab are always `micro`. In the v3 files the sail is identical in every cut and the lane comes out of the swoosh's upper edge, although the kit's prose says the reverse; the files are what ships.
- The kit has two versions of the mark. **Adaptive** (`on-light` / `on-dark`) is for surfaces where our code still picks the file from a background it knows. **Fixed** is for anything that gets copied, installed, cached or shared onto a background we do not control — installed PWA icons, home screens, desktop shortcuts, notifications, link previews. When in doubt, fixed: it never becomes unreadable.
- Installed web copies live in `public/` (favicon pair, apple-touch, the four manifest icons, safari pinned tab). The Tauri manager owns `src-tauri/icons/icon.ico` and `assets/icon.svg` in the separate `Villow-Setup` repository. The retired `public/app-icon.svg`, placeholder Setup V mark and its `scripts/create-icon.mjs` generator are gone; do not reintroduce a generated stand-in.
- In `index.html` the `.ico` link must stay **above** the `.svg` link and keep `sizes="32x32"`. Without that Chrome prefers the `.ico` and the tab icon stops following the browser's light/dark setting. Exactly five icon-related tags belong in the head; the tab icon follows the *browser*, not the app's theme toggle, so never wire `favicon.svg` to `ThemeContext`.
- The kit asks for `background_color: "#1D2736"` in the manifest. This repo does not do that, deliberately: `manifest.webmanifest` and `manifest-dark.webmanifest` are a themed pair whose `background_color`/`theme_color` must differ, which `src/utils/appManifest.test.ts` pins and which exists because an installed standalone window colours its status bar from the manifest. The `purpose: "any"` icons are the fixed palette, so they stay readable on either splash colour.
- The in-app mark is **not** a kit file. `AppLogoMark` inlines the kit's paths for all three cuts, copied verbatim into `LOGO_CUT_PATHS`, and tints them from the active appearance palette, which is a product feature: 11 nature presets, custom colours and the detailed image logos in `images/app-logos/`. Its `cut` prop defaults to `standard`; the 24-32px header, mobile top bar and break-timeout logos pass `small`, and the appearance preview passes `micro` because `ScaledPreview` draws its 32px mark at about 9px on a phone. A placement whose size changes with the viewport takes the cut for its smallest rendering. `logoTop` and `logoBottom` are the brand anchors for that tinting, and the default Fern palette carries the kit's adaptive start stops (`#00c394`/`#002020` light, `#b7fedc`/`#00eec0` dark) so the shipped default renders the real brand mark. Swapping the tinted mark for the kit's `on-light`/`on-dark` files would delete the customisation and needs a product decision first.
- Any deployment that changes icons, the head or a manifest must bump `APP_SHELL_VERSION` in `public/sw.js`, and an installed PWA only re-reads the manifest on its own update check.
- The **"Villow" wordmark** beside the mark is `src/components/Wordmark.tsx`, set in Varela Round. It is the name in every lockup: Login, AccessRevoked, PermissionsRequired, Setup, the desktop header (shown down to a 720px window, 820px with an undo button and 1000px with the rating pill: the maintainer wants it stubborn, and capping the header search at 40rem instead of 56rem - also their call, it was too big - is what leaves room for it), the mobile top bar and the appearance preview. It is tuned entirely through five variables on `:root` in `src/index.css` - `--villow-wordmark-size`, `-scale`, `-tracking`, `-weight`, `-ink` - and the component's `size`/`tracking`/`ink` props override them per lockup, which is how Setup's smaller 40px lockup gets a 27px wordmark and the header's 32px marks get 21px, the same 2:3 proportion as Login's 48/32. `-scale` multiplies every lockup's own size. ## Data And API Guidance

- **The daily cron does not pull subscription feeds.** Home's first visit each local day runs the feed update for everyone (`useDailyFeedCheck`, `last_user_sync`), so feeds behave the same for the host and members. The cron (`handleCronSync`) renews each active account's saved Google sign-in only to run per-account maintenance (country recommendations, the III.E.4 metadata refresh, the shared recommendation feed) and records one `sync_job_runs` row per account (`run_type = 'account_maintenance'`, with its own `duration_ms`). The night is bound by sequential round trips, not work, so it runs in passes inside `SYNC_FUNCTION_BUDGET_MS` (45s of the 60s `maxDuration`): first the III.E.4 refresh for every account, three at a time, least recently maintained first; only then recommendations and the shared feed, oldest `last_recommendations_sync` first, where accounts not reached count as `recommendationsDeferred`, never as failures. Never put anything ahead of the refresh pass. `runDailyCleanup` (log/room/queue purges, fortnight snapshots before the viewing-review purge, which also expires the watch-page metadata cache) needs only the database and runs alongside both passes. Recommendations reuse the token the pass just renewed. The `[cron]` log line times each pass. A refused renewal stores Google's allowlisted reason as its error code (`google_signin_expired`, `google_client_rejected`, `google_token_unreadable`, `google_unavailable`, from `lib/google-refresh.ts`) plus a fingerprint of the stored token; expired/unreadable sign-ins wait until a newer token is saved instead of retrying daily, and never count as a failed cron run. Before the account loop it removes expiring YouTube details for those waiting accounts (see the retention notes below). Leftover `cron_daily` work rows are pruned in bounded batches and ignored everywhere. Testing-mode OAuth expires sign-ins after seven days; the host accepts weekly sign-in, so an inactive member's expired sign-in is expected, not an incident. A YouTube 401 is classified as `session` (sign in again), not host configuration.
- **System health explains each person from evidence**: latest app open (30-day `app_open_events`), Home size against the 100-video limit, unfinished Home updates, their last daily maintenance result, and **Saved video details**: how many of their saved videos, videos in playlists they own and own playlists still hold YouTube details older than 30 days (should be 0; above 0 needs a look) and how many cleared ones are waiting to be fetched again, each counted separately in the copied report. Inactive people and full Homes are healthy states; "opened Villow but Home has not updated for 36 hours" is the actionable signal. The copied report includes every check/job/account summary (fixed server text with no names), the account number on each incident, allowlisted request action/method/code, and the latest daily maintenance runs. Settings conflicts (`settings_conflict`), ratings with no finished record (`outcome_not_found`) and videos whose creator turned comments off (`commentsdisabled`, stored lowercased) are handled by the client and excluded from incident reads. **Database updates** spot-checks one visible change per recent migration through `lib/schema-markers.ts`; add a marker (or an `UNDETECTABLE_MIGRATIONS` entry for constraint/data-only changes) with every new migration, which `schemaMarkers.test.ts` enforces.

Older extensions refund every removal. Only `net_saves` may be compared against `save_limit`; comparing gross to that ceiling reads over 100% for someone who never hit their limit. `save_count - net_saves` is the count of released slots, floored per day because the two are filed under different local days. - `attention_outcomes.from_extension` records whether a video arrived through the extension, **stamped when the outcome is recorded** rather than joined back to `videos` later. Both remove paths hard-delete the video row, so a video that was skipped and then cleared away — exactly the case this measures — would have nothing left to join to. Same rule as the append-only save counter: record the fact while it is true.
- That gives the YouTube row a follow-through signal the usage rollup cannot see: `extension_usage_daily` knows the moment of saving, this knows the verdict, sometimes weeks later. Client cache state must store the global default in `dailyLimit` and today's schedule/group override in `scheduleLimit`; never infer that one should replace the other merely because their numeric values happen to match. That ambiguity caused settings refreshes to temporarily unblock an already-exhausted scheduled limit.
- The watch-time limit editor emits a live preview for every held-arrow step. Keep those events lightweight: the active draft owns the Header limit until that exact draft saves, preview steps must not each append a debug entry or enqueue an IndexedDB write, and access-boundary transitions should still be recorded. A finite zero limit is a weekday ban with 0% remaining, not the full-ring unlimited state; raising it again must clear only the `weekday_limit` ban marker while preserving a real manual date ban.
- The two halves are stored apart and combined on read. `extension_usage_daily.active_seconds` is per browser and absolute; `watch_time_history.watch_time_seconds` is a running counter. Merging on write would multiply the same minutes by however many times the extension resent them. `api/watch-time-history.ts` returns `watch_time_seconds` already combined plus `external_youtube_seconds` for the breakdown, so graphs, averages and the day detail all pick it up without their own arithmetic.
- For **today**, the same sum comes from `user_settings.daily_external_watch_seconds` — an absolute mirror the usage endpoint recomputes via `refresh_daily_external_watch_seconds`. It lives on `user_settings` because that is the row every limit check already reads on every watch tick. Always read it through `combinedDailyWatchSeconds()`; never compare `daily_watch_time_seconds` to a limit on its own. It is stripped from settings PUT bodies so a client cannot write back a stale figure.
- Today is served from the settings mirror and excluded from the history merge in both the full and `summaryOnly` reads. Counting it in both would double it for anyone summing history plus today.
- In `WatchTime.tsx` a day is `video + idle + YouTube = watch_time_seconds`. Idle time is Villow-only, so it clamps against the day minus its YouTube share (`getVillowSeconds`) — clamping against the whole day lets a long YouTube session inflate "idle" and shrink the channel breakdown. A paused watch page counts as idle usage; comments do not have a separate timer or classification.
- **The hourly watch pattern excludes YouTube time**, and says so in the UI. The extension reports a daily total with no hour attribution, and spreading it across the day would invent a pattern that was never measured. If the extension ever reports hourly buckets, this is the thing to revisit.
- `video_viewing_sessions` is intentionally bounded detail, not a permanent second library. One client session id represents one visit to Villow's watch page and its absolute `watch_time_seconds` total makes autosave retries idempotent. The nightly sync calls `purge_viewing_review_history`, which removes sessions after 30 days and stale watch-page metadata/comment cache rows. Viewing Review never inserts pre-watch skips; `get_viewing_review_outcome_aggregates` exposes only grouped channel/source skip counts.
- Removal previews preserve `attention_outcomes.video_title` before the feed row disappears, copying `videos.metadata_refreshed_at` into `video_title_fetched_at` without restarting its retention clock. The review read may recover older missing titles with one cached batch of at most 50 ids; never fetch on hover or write partial titles into the full watch-page metadata cache. Failed batches change nothing, successful omissions are cached for one day, and the nightly review purge clears titles after either 30-day window expires. Apply migration 150 for title storage; the write helper preserves the removal itself during an older-schema rollout.
- Browsing/idle page context remains coarse: `browse_usage_hourly` stores aggregate seconds by day, hour and stable surface category, never URLs. Migration 162 separately keeps thirty days of observed browse/video intervals for the timeline. `activityIntervalRecorder` checkpoints locally every five seconds and stops at observed ticks across shutdown, suspension and clock gaps; AFK while the visible app stays open still counts. Its account-scoped durable queue retries absolute interval ends with stable IDs. `UsageContext` batches browsing into the existing thirty-second upload; playback detail shares existing playback saves and never charges playback totals again. The database applies only previously uncounted browsing seconds atomically, splits them into their actual timezone day/hour and discards expired retries. Do not fall back to non-idempotent browsing deltas when the migration is missing: apply it before the frontend. Successful uploads update the open history cache locally without polling; failed uploads back off. Preserve made-for-kids tracking exclusion. Historical days before migration 148 may lack surface data, and days before interval recording legitimately have only aggregate browsing totals. Verify retries, concurrency, permissions, timezone splits and retention with `node scripts/test-viewing-activity.mjs` and the recorder/timeline/cache tests.
- `attention_outcomes.outcome` classifies whether any playback occurred, so a Skip/remove press on a video with existing progress is deliberately scored as `watched`. `attention_outcomes.resolution` separately preserves the button action (`skip` or `done`) for Viewing Review's activity timeline. Use `resolution` for explicit-removal events and `outcome` for skip-rate scoring; historical watched removals from before migration 141 cannot be reconstructed.
- A worth verdict supplied during playback, completion, or removal is immutable in Viewing Review ("Not sure" is not a verdict and stays open). An outcome that was still unrated when Viewing Review opened may be set to worth/not worth, cleared back to unrated, and corrected repeatedly only while that mounted page session remains open; leaving or reloading locks the saved choice. Verdicts are video-wide: every visible session and every watched `attention_outcomes` row for that video changes together. The component tracks just-edited video ids in memory, applies the choice optimistically without a loading lock, queues background writes per video, and mirrors it through `videoRatingMemory` so the next watch page opens with the same choice. `reaction_editable` is provenance for an outcome initially saved without a verdict, not permission to show every non-null deferred verdict as editable forever, and editability must never be inherited from an older outcome for the same video. A real viewing session with no attention outcome may create an unrated outcome on its first Viewing Review rating, then fill it.
- `definition_version` on a usage row is not decoration. Version 1 required a home feed tile to dwell before counting it, so a fast scroll recorded almost nothing; version 2 counts a tile that reached the viewport. Scoring compares only days sharing the newest version; display shows every day, since a day's own minutes are not a comparison. The column is nullable on purpose — a row the save counter created has no version because no rollup described it.
- `recommendationsSeen` is **home feed only** — not the watch page sidebar, end screens or the Shorts shelf — because that is exactly what the extension's cap governs. Deduplication is per browser per day, so summing across browsers slightly over-counts; call it "videos you were shown", never "distinct".
- A web page cannot link to a `chrome-extension://` options page, and `externally_connectable` cannot help because it needs a static origin list and every self-hosted instance differs. The settings panel and every extension attention action therefore end in instructions, not a link.
- The `channels` table is the subscription list — rows are created on subscribe and deleted on unsubscribe — so `GET /api/subscriptions` needs no YouTube call for ids or titles. Handles are the exception: `channel_url` is always written as the /channel/UC… form, so `channels.handle` is filled from `snippet.customUrl` once per channel and kept. Most YouTube feed tiles link by handle rather than id, so dropping that field would make the extension's match fail on the majority of videos.
- Handles are stored and returned in one shape: no leading `@`, lowercased. A legacy `customUrl` such as `c/SomeName` is rejected rather than stored, since it could never match a tile.
- Extension pairing tokens are stored as a SHA-256 hash in `extension_tokens` and the raw value is returned exactly once, inside the connect link's URL fragment. Never log one, and never move it into a query string: fragments are not sent to servers, which is what keeps it out of access logs, proxies and referrer headers.
- A connect link is a key to one person's queue, not to one browser. Nothing binds a token to the machine it was pasted into, so the same link works on every browser someone owns. Several links can be live at once for exactly one reason: so one can be removed on its own, which is why setup suggests one link per browser. Connected browsers lists one row per link with an × to remove it, named only by the browsers that have reported through it (`client` plus the platform detected from the extension's own request), never by a user-chosen label. Do not add browser fingerprinting, device binding, or a name guessed from the Villow page's user agent — the UI once did the last of these and it taught people a model the code does not implement.
- Nothing ever expires or revokes a token on a person's behalf. `MAX_ACTIVE_TOKENS` caps how many can exist and refuses to mint one more; it never turns an existing link off, because a link someone forgot about may still be the one saving their videos.
- `/connect` is deliberately a public route. Putting it behind `ProtectedRoute` would redirect an unauthenticated visitor to `/login` and drop the fragment, destroying the only copy of the token.
- YouTube API quota matters. Prefer cached data, batch operations, and existing quota accounting helpers in `lib/api-usage.ts`.
- Group playlists are Villow-owned shared data: catalog membership, in-app add/remove, and reorder operations live in Supabase. Sharing an existing personal playlist creates a separate group catalog and copies the complete current YouTube snapshot with local item IDs. Keep the original YouTube playlist and personal catalog untouched; later changes to either copy do not sync. Group playlists have no YouTube refresh action or import inbox; the API rejects explicit group refreshes and creating a group makes no YouTube playlist. Existing inbox records remain only for creator-only conversion back, which exports every shared video before removing group access and restoring personal sync. The pin picker lists Unpinned playlists without Select all and offers Create & pin playlist; pin retries reuse the newly created playlist.
- **`lib/metadata-retention.ts` is a compliance requirement, not an optimisation target.** YouTube API Developer Policies III.E.4.c allows stored YouTube metadata to be kept for no longer than 30 calendar days unless it is re-fetched from the API, which restarts the clock. The retention pass rides the existing `/api/sync` cron and refreshes rows older than `METADATA_REFRESH_AFTER_DAYS` (25, deliberately below the 30-day ceiling so a cron that fails for a few days does not push data over it). Do not delete it, do not raise the window past 30, and do not "save quota" by skipping it — a `videos.list` call is 1 unit for 50 ids, so a 2,000-video library costs about 2 units a day.
- Retention has one rule that must never be relaxed: **a failed batch touches nothing.** An id can come back without metadata because the request failed (quota exhausted, offline, non-2xx) or because YouTube answered and omitted it. Only the second means the video is gone and its metadata may be cleared. Confusing the two lets one bad night wipe a person's whole library. `src/services/metadataRetention.test.ts` pins this.
- `metadata_refreshed_at` and `metadata_enriched_at` are different columns on purpose. Enrichment asks "was this scraped row ever upgraded, and is it made for kids"; retention asks "is this row's metadata still fresh". Overloading one would make the enrichment pass stop finding rows, since it selects on `metadata_enriched_at IS NULL`.
- A video the API no longer returns has its descriptive fields cleared but keeps `video_id` and `channel_id`. Those identifiers are what the person's own save is addressed by; dropping them would delete their library entry rather than expire YouTube's description of it.
- **People who stop using Villow** cannot be refreshed: there is no server API key, so a row is re-fetched only with its owner's own sign-in. When an account's latest `account_maintenance` run refused the sign-in that is still saved (`google_signin_expired` or `google_token_unreadable` with a matching token fingerprint, `getAccountsAwaitingSignIn` in `api/sync.ts`), the cron's `clearUnrefreshableVideoMetadata` clears the same descriptive fields as for a gone video from that account's rows older than 29 days (`UNREFRESHABLE_CLEAR_AFTER_DAYS`, a day inside the ceiling because the job runs once a day). Rows, ids, `published_at` and all Villow state (membership, order, progress, ratings, pins) stay, and `metadata_refreshed_at` keeps its old value so the row is first in line for a refresh. An unavailable Google, a rejected OAuth client, a failed batch, a later successful run or a newer saved sign-in never clears anything. `title` is NOT NULL, so an empty title marks a cleared row; `countExpiredMetadata` and System health count only rows still holding details. When the person signs in again, every Home and Library read (subscriptions, Saved from YouTube, country and friend recommendations, Watch Later, Search's own videos) passes its rows through `restoreClearedVideoDetails` before responding: cleared rows due a refresh are re-fetched with their sign-in (at most 500 per read, three batches at a time), written back and patched into the response, so the cards come back as they were. Rows with titles cost nothing, a video YouTube recently confirmed gone is not asked for again on every read, and a failure touches nothing (the next read or the nightly refresh retries). A refresh writes a thumbnail only to a row that has none, so an extension save keeps its own larger picture. `useDailyFeedCheck` is unchanged: the restore runs inside the Home reads alongside the feed check. Saved playlists follow the same rule in `lib/managed-playlist-retention.ts`: for the same accounts, `clearUnrefreshablePlaylistMetadata` clears the playlists the person owns older than 29 days. Their videos lose title, channel name, thumbnail, publication date and length; ids, `channel_id`, `position` and `made_for_kids` stay (the last keeps Made for Kids tracking off until fresh details arrive), and an empty title marks them. Their own (non-group) playlists lose description and cover; `sync_title`, privacy and counts stay. `metadata_refreshed_at` is NOT NULL in both tables and keeps its old value. Membership and `playlist_video_progress` are never touched. Group playlists (`is_villow_group`) are shown to every member, so every member's daily maintenance also refreshes the videos of the group playlists they belong to (`selectRefreshableCatalogIds`, with that member's own sign-in and quota); a refused owner's group videos therefore only reach 29 days once nobody in the group could refresh them. A group playlist has no playlist on YouTube: its cover is a copy of one of its videos' pictures, so it is renewed from them (`refreshGroupCovers`) and stamped with that video's `metadata_refreshed_at`, keeping the same picture while its video has one and otherwise taking the first video by position with a picture; the refused owner's job clears a cover past 29 days like the videos, and its name and description, the group's own, stay. Group add-video copies the adder's `videos` row with that row's `metadata_refreshed_at`, and keeps already-cleared details cleared so the next read restores them. `handlePlaylistCatalogGet` in `api/sync.ts` passes its rows through `restoreClearedPlaylistDetails` before responding: the Library overview restores the person's own cleared playlists (`playlists.list`), and opening one also restores its cleared videos (`videos.list`); for a group playlist any member does this with their own sign-in once `getPlaylistCatalogAccessContext` has confirmed membership. The same 25-day due check, 500-row cap, sign-in and failure rules as Home apply. The nightly refresh restores the rest. `countExpiredManagedPlaylistMetadata` skips cleared rows.
- Country recommendations use YouTube country charts plus the local category/channel diversity selector. Do not add Gemini calls or require a Gemini API key. The Gemini usage schema and analysis row are retained only as an inert historical placeholder and should remain at zero.
- Things to do uses `ThingsToDoList` in the watch sidebar, workspace and Settings. Collapsed rows have a top-aligned completion mark, up to three title lines and two smaller description lines with ellipses; no provider logo, pencil or disclosure arrow. Clicking the row or pressing Enter/Space opens full-width growing text fields in place without focusing the title or outlining the fields. Only one task is expanded per list, including completed tasks; switching preserves hidden drafts and marks changed previews Unsaved changes. The provider logo opens `TaskDestinationMenu` immediately after the deadline in the Save/Cancel footer, or at the left if undated. Optional bedtime controls share that footer; nothing sits above the title. Save/Cancel close the editor and errors preserve the draft. `useTaskExpansionAnimation` uses the chosen Slide only reveal: 280ms of measured height with fully visible text, on desktop and mobile (see DESIGN_TASK_EXPANSION.md). Google Tasks and Todoist marks retain their shapes but use the footer text colour; Todoist ticks are transparent cutouts. Completion and link clicks never expand a row. Mouse pointer capture starts only after the drag threshold, so ordinary clicks reach the summary. Preserve mouse/touch reordering and Alt+arrow ordering when no editor is open. Recently completed tasks use the same previews; their checked mark brings them back.
- Things to do writes to Google Tasks/Todoist, not just reads. A task is created in the provider first and mirrored locally only once it exists there, so a provider failure cannot leave an orphaned Villow row. Edits to a mirrored task similarly update the provider's title and notes before changing the Villow row. Moving a task between destinations creates the new provider copy before deleting the old one, for the same reason. `task_integrations.selected_external_lists` holds titled copies of the mirrored lists so the destination picker never has to spend provider quota.

## Coding Practices

- Home Undo restores a video's original position among surviving neighbours and preserves its original timestamps. Keep the source feed cache and account-scoped query in sync; stale feed/status replies must retain pending restores, while a newer removal supersedes them. Late success/failure callbacks from an undone action cannot hide or resurrect the card. Ordinary delete/restore/Watch Later requests for the same account/video run in order through retries while their optimistic UI stays immediate. Cover real Watch completion and VideoFeed actions with deferred replies, including two restored cards followed by removal of the remaining third card.
- Saved playlist rows can have a title before their channel, thumbnail and date arrive. `restoreClearedPlaylistDetails` repairs these partial rows on ordinary reads even with a recent save stamp; complete rows need no lookup, and confirmed unavailable rows retain the existing cooldown. Malformed/failed reads change nothing; retain known Made for Kids protection on omissions. Channel/date placeholders pulse with the thumbnail while pending and become static when unavailable. Watch navigation handoffs seed the queue immediately but must still read confirmed pending metadata; confirmed saves supersede older reads. Post-save metadata reads must preserve newer playlist edits, saves, removals, order and progress, and ignore superseded or departed-view responses. No schema or deployment change.

- An open watch sidebar must not suppress the native document fullscreen request; preserve its content and the playing iframe through entry/exit, including the desktop sidebar's mounted reader. Preserve midnight normalization and same-day counter ordering.
